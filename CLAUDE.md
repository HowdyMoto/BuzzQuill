# CLAUDE.md — working in this repo

BuzzQuill is a browser-based SVG vector editor (TypeScript + Vite, no framework) that aims to stand in for both Illustrator and Figma. This file is the orientation an agent needs to change code here without breaking things. Keep it current when you change the architecture.

## The model (read this first)

**The DOM is the source of truth, not the model array.** Shapes live as real SVG elements in `#drawing-layer`. `AppState.shapes` (`core/state.ts`) is a tree *derived* from that markup by `rebuildShapesFromDOM()` (via `detectType` + `readStyle`). After any structural DOM mutation, call `rebuildShapesFromDOM()` so the two never drift. Every element that should be a selectable layer carries a `shape-N` id.

**History is an innerHTML snapshot of `#drawing-layer`.** Undo/redo swap the markup and rebuild. Two consequences that cause most bugs here:
- **`<defs>` is NOT in the snapshot.** Anything in defs (effect `<filter>`s, `<marker>`s, gradients, patterns, grid patterns) is a *regenerated cache*. Its parameters must live as `data-*` attributes on the element so they round-trip; the def is rebuilt after each rebuild/restore (`effects.ensureFilters()`, `markers.ensureDefs()`, …).
- For anything you add to the tree, prefer encoding state as `data-*` attributes on elements so it survives the snapshot for free.

**Frames = Figma containers, not the old artboards.** A frame is `<g data-frame>` in the drawing layer, holding its own `<clipPath>`, a `.frame-bg` rect, and children in frame-local coords. `AppState.artboards[]` is a *derived cache* over top-level frames (`frameToArtboard`); `activeFrameId`/`selectedFrameId` hold **frame shape ids**. **Legacy-name trap:** the tool, renderer and `data-tool` value have all been renamed (`tools/frame-tool.ts`, `ui/frame-renderer.ts`, `data-tool="frame"`), but the **model layer has not**: AppState's frame API is still `addArtboard`/`updateArtboard`/`getArtboardById`, and the derived cache is still `AppState.artboards[]`. So the split is UI-says-frame, model-says-artboard — grep **both** when hunting frame code, and don't trust either name to be the whole story.
- Frames are **transparent to click-selection** (clicking a shape selects the shape, not the frame) and **cannot be rotated** (export/rulers/grid assume axis-aligned).
- Frames are **top-level only** — never nested in a group or another frame. Enforced in `addFrame` and `LayerManager.moveShape`/`groupShapes`/`groupSelectedShapes` (frames are filtered out). Ordinary shapes/groups still nest freely.
- **Auto-parenting** a freshly-drawn shape (`addShape(shape, originPt)`): the frame you *started* the draw in owns it (Figma rule), else the shape's world bbox center-inside-or-majority-overlap picks the frame (`frameForWorldBBox`). Same overlap test drives `reparentAfterMove`.
- Per-frame **grid + rulers** are editor chrome (rendered in an overlay, config in `data-grid-*`/`data-frame-rulers`), never exported.
- New frames default to a **transparent** `.frame-bg` (`fill:none`) — just the outline chrome; existing saved docs keep their stored fill.

**Wrapper-cache leaf pattern** (`data-boolean`, `data-clip-group`, `data-appearance`, `data-width`). Several features wrap a shape in a `<g>`, store config in `data-*`, and keep *regenerated render children* that round-trip via the snapshot. `rebuildShapesFromDOM` models the wrapper as a **leaf** and never walks its generated children (they carry no id, so no phantom layers). Appearance/width **unwrap to a plain element** when the config becomes trivial. The object-level attributes moved onto the wrapper live in `core/wrapper-attrs.ts` (`CARRY_ATTRS`) and are moved with `moveObjectAttrs` / `carryObjectAttrs`, never a hand-written loop.

**Object-level attributes are all attributes — including blend mode.** `data-blend` is the source of truth; the inline `mix-blend-mode` that renders it is written only by `setBlend` (`core/wrapper-attrs.ts`), and `CompositingManager.ensureBlend` adopts inline-only styles after every rebuild. Read a blend mode with `getBlend`, never `el.style.mixBlendMode`. Guarded by `guard:object-attributes-travel-as-one` (which also scans `src/` for a second writer).

## AppState decomposition — the dominant pattern

`core/state.ts` is the historically-huge `AppState`. It's being decomposed into **collaborator classes**, each reaching AppState through a **narrow typed host-seam** (an `XxxHost` object literal built in AppState's constructor with arrow closures — never a back-reference to the whole AppState). AppState keeps **thin delegating methods** so external call sites never change.

Current collaborators (all in `core/`): `history`, `paint-registry` (gradients/patterns, via `document-context` — deliberately paint-only), `pattern-links` (`PatternLinkManager` — patterns made from artwork, linked refresh, edit/unlink), `clipboard`, `symbol-registry`, `text-styles` (`TextStyleRegistry` — document-scoped text styles persisted in a `<metadata>` carrier, re-derived on every rebuild), `effects` (blur/shadow filters), `compositing` (blend mode/opacity/canvas backdrop), `selection-style` (`SelectionStyleManager` — the fill/stroke/cap/join/align/radius/effect writers behind the paint controls), `markers` (arrowheads), `appearance` (fill/stroke stacks), `width-stroke` (variable-width), `pathfinder` (boolean/shape-builder/outline/offset), `corners` (`CornerManager` — Round Corners / Smooth over the selection, plus the preview/commit/cancel trio the Round Corners dialog drives), `path-join` (`PathJoinManager` — Join ⌘J: close an open path, join two at their nearest ends in the upper path's own space, or join the two end points selected in node editing; coincident ends merge into one anchor that keeps both curves), `layers` (z-order/lock/duplicate/group/ungroup), `library-styles` (`StyleLinkManager` — which objects use which library style, and the detach-by-reconciliation policy; `LINK_ATTR` is the single link-attribute table), `path-direction` (`PathDirectionManager` — Reverse Path Direction: rewrites the written point order and nothing a person can see, mirroring whatever is measured along the path; its chrome and flourish are `ui/direction-overlay.ts`, in `#direction-layer`, shared by the Direction tool and the command). `coords.ts` holds the shared CTM math.

Several `core/` modules are used directly by AppState or the tools but are **helper modules, not host-seam collaborators**: `boolean` (the paper-core engine — imported by both `pathfinder` *and* AppState, not only via pathfinder), `rect-shape` (the `data-rect` corner-radii leaf), `stroke-align` (`data-stroke-align` inset/outset clips), `bake` (bake a transform into geometry, used on export), `export-scope` (what an export contains and where its edges are: hidden layers are stripped from every export, and "Fit to paths" narrows the viewBox to the visible geometry without moving any coordinates), `snapping` (drag snap targets), `locks` (`isLockedEl` — what a lock means on the canvas: a press passes through locked artwork, including everything inside a locked group/frame, and a locked selection gets no handles; tools resolve every press through `BaseTool.unlockedTarget`, so a new tool that picks shapes must too — guarded by `guard:locked-shapes-stay-put`), `shape-props` (per-type capability predicates — the seed of a real shape-type registry), `session-store` (IndexedDB session restore, used by `main.ts`/`document-manager`), `author-styles` (hands paint from an imported `<style>` — Illustrator's `.cls-1{…}` — over to presentation attributes on every rebuild and before an append merges, since any class rule outranks the attributes the editor writes).

**To add a feature subsystem:** put the logic in `core/<name>.ts` as a manager class + `<Name>Host` interface; build the host in AppState's constructor; add delegating methods on AppState. Verify behavior-identical in the browser before committing. Some helpers (`selectedInDomOrder`, `commonParentOf`, `convertShapeToPath`) are genuinely shared across grouping/clipping/pathfinder — they stay in AppState and are surfaced through hosts.

What legitimately **stays** in AppState: the shape model + `rebuildShapesFromDOM`, history capture/restore, the frames model + grid/rulers, selection, defs import/export, group isolation, clipping, the node-edit session. That's the irreducible core, not a grab-bag.

## Coordinates

- **Screen → world:** `Canvas.screenToSVG()` (`core/canvas.ts`) — the single entry point; every tool feeds pointer coords through it. It's manual viewBox math, not CTM-based.
- **Element-local ↔ drawing-layer:** use `core/coords.ts` (`worldToLocal`, `localBBoxInLayer`). Don't re-inline `parentCtm.inverse().multiply(elCtm)` — that duplication was already consolidated.

## Build & tooling constraints (these WILL bite you)

- **`erasableSyntaxOnly` is on:** no TS constructor parameter properties (`constructor(private x)`), no `enum`. Use an explicit field + assignment.
- **`noUnusedLocals`/`noUnusedParameters` are on:** unused imports/locals fail the build. After removing code, prune imports.
- **Third-party scripts are allowed by host, never inlined.** Google Identity Services and the Picker have no npm bundle; `buildCsp` lists their hosts only when Drive is configured. Don't widen `script-src` for anything else without the same gate.
- **Paper.js must be `paper-core`, never `paper-full`** (aliased in `vite.config.ts`). paper-full uses `new Function()`, which the app's strict CSP blocks. `paperjs-offset` powers outline/offset.
- **Fonts for outlining are TTF, decoded at build time.** Outline Text reads glyphs with opentype.js, which can't read WOFF2 — and the variable faces the canvas renders with ship only as WOFF2. `import url from '…/face.woff2?ttf'` gives the URL of a TTF decoded by the `woff2-to-ttf` plugin in `vite.config.ts`, using `wawoff2`: a devDependency, because it is WebAssembly and the CSP forbids that in the browser. A variable family is outlined from that face at the axis values the browser used (`variationFor` in `core/text-outline.ts`: opsz from the size, wght, wdth, explicit variation settings), never from a static file, which is one fixed instance of the design. Guarded by `guard:outline-text-matches-variable-fonts`.
- Typecheck: `npx tsc --noEmit` (fast, ~2s). Build: `npm run build`. **Caveat:** the user often has parallel uncommitted WIP in shared files, so a failing typecheck may be pre-existing — diff against HEAD before attributing an error to your own change.

## Dev & QA workflow

- Run an **isolated** dev server so you don't collide with the user's: `npm run dev -- --port 52xx --strictPort`.
- QA with Playwright — it's a devDependency, so resolve it from the project's own `node_modules` (`scripts/smoke.mjs` does this via `createRequire`) rather than a machine-specific npx cache path. DEV builds expose `window.state` (the `AppState`) and `window.docs` (the `DocumentManager`) — drive the real app through them.
- For refactors, **verify behavior-identical with real operations and assert zero console errors** — collect `pageerror`/`console.error`. Exercise the touched feature end-to-end (draw, transform, undo/redo, save/reload round-trip), like a power user.
- **Smoke test** (`npm run smoke -- <port>`, or `node scripts/smoke.mjs <port>`, against a running dev server): drives the {operation × shape-type} matrix and fails on any console error, including the dev invariant. Run it before a PR that touches shared shape/frame code; extend the matrix as the app grows.
- **UI walkthrough** (`npm run walkthrough -- <port> <outDir> [headless]`): drives the REAL interface — toolbar, mouse drags, marquee, context menus, typing — and screenshots each step. Model-level checks can't see what the screen SHOWS; this harness has caught a CSS escape rendering as mojibake, a panel frozen mid-edit showing stale state, and success toasts wearing a warning icon. Run it for any change that touches panels or chrome.

## Recurring bug patterns (learned the hard way — check these on every change)

These causes account for the large majority of shipped bugs here. Most were **the same fix needed in another place**, or **generic code not handling a special type** — so verifying the *invariant* and the *sibling paths* beats just re-testing the case you touched.

1. **Derived caches drift.** `AppState.artboards` is *derived* from the frame `<g>`s; every mutation must re-derive it (`syncArtboardsCache` / `syncFrames` / `rebuildShapesFromDOM`). Forgetting it → a deleted frame's outline lingers, a pasted frame isn't selectable, a dragged frame's chrome lags. **Guarded by `AppState.devCheckFramesInvariant()`** (dev-only, wired into `onStateChange`): it logs a `[frames-invariant]` `console.error` the instant the cache disagrees with the DOM — so QA/console catches it automatically. When you add a frame-mutation path, this backstops you; don't remove it. Effect filter regions are the same trap: they're absolute (`userSpaceOnUse`, sized from `getBBox`), so a nudge or a Transform-panel edit that doesn't rebuild left them behind, clipping or hiding the shape — they're refit every render frame (`state.refreshEffectRegions()`, beside `refreshStrokeAlignClips`). Guarded by `guard:effect-regions-follow-geometry`.
2. **`getBBox()` is LOCAL, pre-own-transform.** It is NOT the world/rendered box. For positioning, hit-testing, or reading a shape's coords, use `localBBoxInLayer` / CTM math (`core/coords.ts`) so the element's own transform *and* ancestor (frame) transforms are included. Naive `getBBox()` caused wrong-frame outlines, group-into-frame failures, and stale Transform readouts. Grep new `getBBox(` uses in positioning code.
3. **Per-type dispatch gaps — and "a frame is a `<g>`."** `switch (tag)` / `if (type === …)` chains routinely miss `path` / `polyline` / `polygon` / `line` / `group`, and a **frame (`<g>`) silently falls into the generic group branch** (it got *scaled* instead of resized). When you touch such a chain, cover every shape type and special-case frames explicitly.
4. **Frames are a special shape that leaks everywhere.** Move / resize / delete / paste / select / clip each need frame-specific handling that generic shape code doesn't provide. Treat "does this work for a frame?" as a required check, not an afterthought.

5. **Replacing an element drops everything it carried, and an "editing session" that rebuilds is a silent data-loss path.** A tool that swaps a shape for a rebuilt one (crop's `<image>` ⇄ `<svg data-crop>`, outline, uncrop) keeps only the attributes it thinks to copy: the crop tool dropped `transform`, so opening a crop on a rotated image flattened it onto its bounding box. Carry the old element's attributes wholesale (`carryAttrs` in `tools/crop.ts`, or `carryObjectAttrs` in `core/wrapper-attrs.ts` — the `CARRY_ATTRS` set plus a hidden layer's `display:none`; `moveObjectAttrs` when the old element stays in the document inside the new one) and deny-list only what you rewrite. **A new `replaceWith` / `replaceChild` site fails `guard:element-replacements-are-reviewed`** until it has been given one of those helpers, a pixel case in the oracle, and a line in that guard's table. The same bug was in boolean flatten, mask flatten, outline stroke, outline text, component detach and repeat release, each with its own hand-picked list. Detach must also give cloned descendants fresh `shape-N` ids (`importNode` keeps them, so two detached copies shared ids). **Mind the coordinate space when moving attributes:** a transform or opacity folded onto a *child* must compose (`[outer, inner].join(' ')`, `composeOpacity`), and a clip or filter is defined in the user space of the element it sits on, so if the new geometry lives in a different space (detach adds the `<use>`→symbol viewport step), keep those on a wrapper `<g>` in the old space instead (`dissolveOnto` / `foldOnto` / `foldsCleanly` in `core/wrapper-attrs.ts` are the shared "a container is going away" helpers — detach and repeat release use them; ungroup, which has many children and must not wrap them, hands each child the group's opacity and re-expresses its effects in that child's space with `inheritEffects`) — or, better, compute the new geometry in the old element's OWN space and carry its transform (mask flatten used to bake the transform in, turning a rotated mask's shadow and shrinking a scaled one's blur). Chrome also drops a nested `<svg>`'s viewport clip once that svg is filtered, so a crop clips one level down, on an inner `<svg data-crop-clip>` (`core/crop-clip.ts`). Related trap: a `<use>`'s `x`/`y` are applied *inside* its user space, so a `userSpaceOnUse` region computed from its `getBBox()` must subtract them (`effects.applyFilter`; unshifted, a blurred instance rendered nothing). Related: **entering and leaving a session unchanged must be a true no-op** — no rebuild, no history entry, and no residue like an empty `style=""` left by a `display:none` preview, since history and saves compare markup. Guarded by `guard:crop-keeps-the-transform`, `guard:rebuilds-keep-what-is-rendered` and `guard:ungroup-keeps-what-the-group-carried` (pixel diffs: a rotated/faded/blurred case, before vs after vs one undo — the shared oracle is `rbCase` / `rbGuard` in `scripts/smoke.mjs`; add a case there for any new path that replaces an element).
6. **Measuring a transformed element in its PARENT's space flattens it.** Mapping a box through a rotation and taking min/max gives the axis-aligned bounding box — the rotation is gone and the box is bigger. Work in the element's OWN space (where its `x/y/w/h` are written, before its `transform`) and let the transform ride along untouched; map only for hit-testing and chrome. The crop tool captures its local↔parent and local↔guides matrices at session start, because a `display:none` element has no CTM to ask later. The same goes for sizes: a radius, a minimum crop edge or a tolerance the user sees in canvas units must be divided by the element's own scale before it's applied to local geometry (Round Corners gave a `scale(4)` rect four times the radius the dialog showed).
7. **Transient editing state leaks into persistence.** Autosave (the session store), tab switches and history all serialize the drawing layer — so anything a session or preview writes INTO the document gets saved as if it were real: a reload mid-crop restored the image hidden, a tab switch saved it hidden and left the crop overlay over the next document, and a reload with the Round Corners dialog open restored the uncommitted preview. Keep session chrome out of the document (the crop session hides its target with a `<style>` rule in the guides layer, not an attribute on the element); where a preview must edit the real element, report it (`state.hasLivePreview()`) so the autosaves skip that moment; and end a live tool session before a tab is serialized (`DocumentManager.saveActiveIntoTab`). Undo is disabled during a crop session — it isn't in history yet, so Undo reached past it. Guarded by `guard:crop-session-stays-out-of-the-document` and `guard:corners-leave-no-trace`.
8. **Commit to the target the edit was FOR, not whatever is current when it lands.** A field or rename that commits on blur resolves its target at commit time, and by then the press that ended the edit may have changed it: the canvas selects on `pointerdown`, before the blur, so a value typed for shape A landed on shape B (fixed by `commitFieldsOnCanvasPress` in `ui/dom.ts`, which blurs the field first); a rename deferred to the click's bubble phase let a tab button switch documents first. A blank "Mixed" field has no value to step or scrub from — stepping it started from 0 and overwrote every selected object. Guarded by `guard:rename-lands-where-it-was-typed` and `guard:fields-commit-to-their-own-selection`.
9. **One element filters, THEN clips.** SVG's order on a single element is fixed: `filter` → `clip-path` → `mask` → `opacity`. So an effect and a clip on the same element never give "clip it, then shadow the result": a mask's own shadow was cut off at the mask's outline, and Chrome goes further and drops a nested `<svg>`'s viewport clip once that svg is filtered (the crop bug). Getting clip-then-effect takes two elements. An effect set on a mask therefore lands on a plain group around it (`EffectsManager.effectHost`, which also takes over the selection, the opacity, the blend and a linked effect style), and a crop clips on an inner `<svg data-crop-clip>`. The same order is why content with an effect of its own can't be baked into a plain path when a mask is flattened — a blurred shape clipped by a mask is not a blurred clipped shape — so such a mask commits its clip instead (`resistsBaking` in `core/pathfinder.ts`). Guarded by `guard:mask-effects-and-flatten` and `guard:crop-session-stays-out-of-the-document`.
10. **Turning a stroke into geometry means reproducing what the RENDERER drew, not the attributes.** Outline Stroke used to widen the centre line and stop. `strokeInk` (`core/pathfinder.ts`) is the one place that knows everything a stroke is on screen: a dash pattern cut into dashes (laid out on the renderer's own `getTotalLength()`, and for an `<ellipse>` starting at 3 o'clock going clockwise — `strokeOrderPathData` — where `localPathData` starts at 9 o'clock); arrowheads, which the renderer scales by stroke width, turns to the path and clips to the marker's viewport (`core/marker-geometry.ts`); square caps; SVG's miter limit of 4 (paperjs-offset defaults to 10); and an inside/outside alignment, which on screen is a doubled stroke with half hidden (`core/stroke-align.ts`) and so must be redone as a boolean against the shape. Flatten Mask uses the same function, because a live stroke on a cut-down shape runs along the cut edge where there never was one. Anything else that vectorizes a stroke should call it rather than `outlineStrokeData` directly. Guarded by `guard:outline-stroke-is-what-rendered`.
11. **Imported artwork isn't shaped like the app's own.** Code written against what the app produces breaks on what a file can contain. A `<symbol>` made here has one child, a padded viewBox and a sized `<use>`; an imported one may open with a `<title>`, hold several shapes, contain a `<circle>` (rebuild converts circles to ellipses only in the drawing layer, not inside `<defs>`), clip content that overflows its viewport, or be instanced with no width/height — which means "100% of the viewport", and here that viewport is the canvas, so the instance resized as you zoomed (`sizeBareInstances` in `core/svg-io.ts` pins it to the file's own viewport at import). `detachInstanceElement` handles all of these; a component is also detached INSIDE other components before it is deleted. When you touch symbol, marker or defs code, test it with a hand-written SVG, not just artwork made in the app. Guarded by `guard:imported-components-detach-whole`. The same goes for path data: minified arcs have no separators between their flags (`a5 5 0 015 5`, which `parsePath` used to drop outright), drawing can continue after a `Z` with no moveto, and artwork in tiny units has real points closer together than `MERGE_EPS`.

**Before declaring a fix done:** (a) grep for **sibling call sites** doing the same operation and fix/test them together — `removeShape` vs `removeSelected` was one bug shipped twice; (b) drive the **real user gesture** (keypress / button / drag), not just the model method — testing `state.removeShape()` passed while the Delete-key path was broken; (c) run against the **shape-type matrix**; (d) test **on-screen, at real scale, with real `shape-N` ids** — off-screen elements and synthetic ids produce false pass/fail in the harness.

## Boot: phones never load the editor

`index.html` loads `src/entry.ts`, not `main.ts`. The entry decides first: a **phone** (touch-only primary pointer, screen short side under 600px) gets the "Built for the desktop" gate (`ui/desktop-gate.ts`) and never downloads the editor; everything else — desktops, tablets — lazily `import('./main')`. So `main.ts` is a lazily-loaded chunk: don't add boot code to `index.html` or `entry.ts` that assumes the editor exists, and keep `desktop-gate.ts` dependency-free (every visitor downloads it). `style.css` is imported by the entry so it stays render-blocking. `?gate` forces the gate on any device for review. Guarded by `gate:phone-never-loads-editor`.

## Multi-document tabs

`DocumentManager` (`core/document-manager.ts`) keeps **one** live `AppState` and swaps document *content* on tab switch (serialize out / load in) — the `state` reference handed to tools/panels at boot never changes. Panels take `state` as a parameter each call. Don't refactor to a per-tab `AppState` without auditing every `setupX` closure — the current design is what makes them safe.

**Document identity is one value with one writer.** *Where* the active document lives is `DocSource` (`core/doc-source.ts`, import-free): `{ kind: 'local', handle }`, `{ kind: 'drive', fileId, modifiedTime }`, or `null` (never saved — Save becomes Save As). It used to be two hand-synced singletons (a file handle and a cloud tether) that every open/save/import path cleared and set by hand, and a missed site meant ⌘S wrote to the previous document's file. Open/import identity changes go through `adoptSource(source, name, onDisk?)` in `ui/project-file.ts` (which also sets the display name and the `diskCopy` flag), the tab swap restores a tab's cached `source`, and save completion updates its captured owner through `DocumentManager`. Per-tab it is `DocTab.source`; the session store persists it and `migrateTab` upgrades pre-DocSource records. Adding a storage backend means adding a `kind` to the union and routing `file.save` by it — never a second singleton. Guarded by `guard:doc-source-has-one-writer` (`scripts/smoke.mjs`), which also fails on any revival of the retired `getCurrentFileHandle`/`getCloudDoc` names. The app runs **no server**: there are no accounts and nothing in `src/` talks to a backend of ours.

**Google Drive is the one third party, and it is browser-only** (`lib/google-config.ts`, `lib/google-drive.ts`, `lib/google-picker.ts`, `ui/drive.ts`). It is a build-time switch on two PUBLIC identifiers (`VITE_GOOGLE_CLIENT_ID`, `VITE_GOOGLE_API_KEY`); unset, no command is registered and the CSP stays `'self'`-only (`buildCsp` in `vite.config.ts` gates Google's hosts on the same vars — `public/_headers` carries them unconditionally and its COOP must stay `same-origin-allow-popups`, or the sign-in popup can't hand the token back). Scope is `drive.file` only: the Picker is what grants access to a file, so `setAppId` must be this project's number. A `'drive'` DocSource makes ⌘S write back to Drive; **there is deliberately no autosave to Drive** — a token can't be renewed without a user gesture (GIS has no browser refresh token, and a new one is a popup), every write is a Drive revision, and v3 has no atomic precondition — so `ensureToken` is only ever called from a click/keypress, and a save compares `modifiedTime` first and asks before overwriting. `test/drive.spec.ts` stubs both Google scripts and `googleapis.com` with `page.route`; it skips itself against a dev server without the env vars.

## Git / PR workflow

**Work in a git WORKTREE — never in the user's checkout.** The user edits this repo
while agents are running. `git checkout` / `git pull` in the primary directory swap
files out from under them mid-edit, and their in-progress work then shows up in the
agent's `git status` as phantom "unexpected changes". A worktree gives the agent its
own directory and branch, so neither side can disturb the other:

```
git fetch origin
git worktree add -b <branch> ../.bq-worktrees/<branch> origin/master
cd ../.bq-worktrees/<branch>
# …work, commit, push, gh pr create…
cd -                                            # back to the main repo FIRST
git worktree remove ../.bq-worktrees/<branch>   # …and drop the worktree BEFORE merging
gh pr merge <n> --merge --delete-branch
```

Tear the worktree down **before** merging: `--delete-branch` cannot delete a branch
that a worktree still has checked out, so merging first leaves a stale local branch
behind that then needs `git branch -D` and `git worktree prune` to clear.

Worktrees live BESIDE the repo (`../.bq-worktrees/`), so they never appear in the
user's `git status` and need no `.gitignore` entry. Branching from `origin/master`
keeps the "always start from a fresh base" rule without running `git pull` in the
shared checkout.

**The user's uncommitted files are expected, not a problem.** Never report them as
unexpected changes, and never stage, stash, revert, or commit them. If a needed file
is dirty in the user's checkout, that's precisely why the work belongs in a worktree.

Never base a branch on another feature branch or a stale checkout — the user merges in
parallel, so a stale base means phantom diffs and conflicts at PR time.

Branch → commit → push → `gh pr create` → `gh pr merge --merge --delete-branch`. Never
commit straight to `master`. End commit messages with:

```
Co-Authored-By: Claude Opus 4.8 (1M context) <noreply@anthropic.com>
```

**The user often has parallel uncommitted WIP in shared files (`style.css`, `index.html`, `state.ts`, panel modules). Stage only the files you changed — never `git add -A` blindly.**

## Panels & UI

Panels follow `setupX(state)` (wire once at boot) + `updateX(state)` (called from `onStateChange`). Centered dialogs go through `ui/modal.ts` (`openModal`, handles stacking + Escape); reusable promise dialogs are in `ui/dialogs.ts`. Design tokens are CSS `--ai-*` vars in `style.css` (+ `ui/tokens.ts` for canvas-drawn chrome). Number inputs get drag-to-scrub automatically via `ui/number-scrub.ts`.

**Handle cursors come from rendered geometry, not handle names.** A resize handle's cursor is picked from the selection box's on-screen corners (`handleCursors` in `ui/selection-overlay.ts`), so it rotates with the shape — including when the rotation comes from an ancestor group/frame, or the shape is flipped. A by-name map (`nw → nwse-resize`) is up to 90° wrong on a rotated object, which is what made resizing one confusing. CSS has only four double-headed arrows, so this quantises to 45°; the axis-aligned multi-selection box still uses the by-name map, correctly. Guarded by `guard:resize-cursors-follow-rotation`.

**A panel rebuild during a press swallows the click.** Panels re-render by replacing their rows (`replaceChildren`), so if a render lands between a click's `mousedown` and `mouseup`, the element under the pointer is gone and the browser dispatches **no click at all** — the user's click silently does nothing. Anything that commits on blur is the classic trigger: `beginInlineRename` (`ui/panel-helpers.ts`) now waits for the press that ended the edit before calling its `commit`, because committing re-renders every panel — it commits in the click's CAPTURE phase (the click's path is fixed by then, yet no handler has run) or right after a `pointerup` that brings no click, never from a timer. If you add a control that mutates state from a blur/focusout, check it the same way — and test with a REAL mouse click, since a synthetic `.click()` needs no surviving mouseup target and passes against the broken build. Guarded by `guard:rename-commit-keeps-the-click`.

**Collapsible-panel header is a design-system pattern, not per-panel wiring.** Every `.panel > .panel-header` gets it for free: markup is `<span>Label</span>` then any right-aligned action button (`.panel-add` +) then `<button class="panel-collapse">▼</button>` **in that DOM order** — CSS (`.panel-header .panel-collapse { order:-1 }`) floats the disclosure chevron to the LEFT so the chevron and the action can't be mis-hit. Collapse toggles two ways, both wired generically in `main.ts` over `.panel-header` (never per panel): single-click the chevron, or double-click anywhere on the bar except its buttons/inputs. New panels need no collapse code — just the header markup. The living reference (`npm run design-system`) renders a `.panel-header` demo.

**Every tool says what it can do, in one strip.** `ui/tool-hint.ts` owns the chip strip at the top of the canvas (`#tool-hint`): `TOOL_HINTS` maps every `ToolName` to a function of state returning chips, so hints are context-aware (a selected path → "Double-click · edit points"; one end point picked on a single run → "⌘J · close path"; two ends picked → "⌘J · join ends"). A keycap holds only a key or a gesture token (Shift, Alt+drag, Double-click), never a sentence; a chip with a `command` renders as a real button in the accent "available now" style and runs that command. The gesture hints (`ui/gesture-hud.ts`: modifier keys DURING a drag, table `GESTURE_HINTS`) render into the SAME element in its bold `.gesturing` style with held modifiers lit — there is one strip, never two boxes; the resting chips of a shape tool are its gesture chips, so the drag continues them. It re-renders on settled renders and on every tool switch; `refreshToolHint()` is for a change no state notification carries (Shape Builder's faces arriving, a text editor opening). `placeContextPopover` keeps the popovers out of the strip's band (it flips below). The strip is visual chrome (`aria-hidden` chips; menus carry the same facts) and View ▸ Show Tool Hints turns the resting hints off (`ui/hint-prefs.ts`, localStorage). Never advertise an operation whose result would be indistinguishable from doing nothing (closing a straight two-point line was). **The contextual popovers are the click targets for the same discoveries**: a single path's bar leads with Edit Points (`ui/path-actions.ts`, inside entered groups too), the Pathfinder bar has Join for two open paths (`ui/pathfinder.ts`); all three popovers refresh together through `updateContextPopovers()` in `main.ts`, which also runs on a tool switch — a shape drawn with a tool lands selected in Select, and a tool switch fires no state change of its own, so the bar used to appear only after the next click. Guarded by `test/tool-hints.spec.ts`.

**The contextual bars share one look and one entrance (`.ctx-popover`, `ui/selection-popover.ts`).** All three bars carry the `ctx-popover` class beside their own; `placeContextPopover` positions them, points the nub at the selection (`--ctx-nub-x`, `data-placed`) and plays the entrance (`.ctx-enter`, bar springs out of the selection, items stagger in seen order) ONCE per new selection — the selection ids are the key. Hide a bar with `hideContextPopover(pop, state)`, never `pop.hidden = true`: it keeps the key while the selection lives, so the bar returns silently after a drag, nudge, Space-pan or tool switch, and forgets it only when the selection is gone. A CSS animation restarts every time an element leaves `display:none`, so never put an always-on `animation` on a bar that hides for gestures — that replayed the old pop after every drag. Guarded by `test/context-bar-entrance.spec.ts`.

**Every slider gets a typeable value — never a read-only readout.** Place `sliderField(range, { scale, unit })` (`ui/slider-field.ts`) right after any `<input type="range">`; `scale: 100` shows a 0–1 value as a percent. The field drives the slider by firing the slider's own `input`/`change`, so the existing live-on-`input` / commit-on-`change` listeners (one undo step) need no changes. Refresh a slider from the model with `setSliderValue(range, v, mixed?)`: assigning `range.value` directly fires no event and leaves the field stale. A typed value snaps to the slider's `step`, so make the step as fine as a typed value should be. Guarded by `guard:slider-value-fields`, which also scans `src/` for a range input built without `sliderField`.

**Direction shows what the file says, and a reversal must not move a pixel.** A closed loop keeps its start point, because that point means something to whoever reads the file (a circuit's start line); an open path swaps ends. Every run of a compound path flips together, or a nonzero hole fills in. Anything measured along a path has to turn around with it: a width profile mirrors `t`, a sideways stroke sets `offsetReversed` and keeps being computed from the source walked the original way (the engine's result depends on direction, so no sign rule can be exact; the on-canvas offset handle reads the flag too), text on the path flips (`flipTextSpan`). Add the next such thing to `mirrorDependents` in `core/path-direction.ts`. Deliberately NOT preserved: an arrowhead stays on `marker-end`, so it moves to the new end and keeps pointing the way the path travels; dash patterns restart from the new start. Rect and ellipse store no order, so they convert to paths and the user is told. Guarded by `guard:reverse-keeps-what-is-rendered`.

## Recipes (the common change shapes)

- **Add a drawing tool:** create `tools/<name>.ts` extending `BaseTool`; add the id to the `ToolName` union (`core/types.ts`); add one row to `TOOL_DEFS` in `main.ts` (`{ label, ctor }` — the label-map and instance-map derive from it, and `Record<ToolName,…>` makes a missing row a compile error); add a `<button data-tool="<name>">` in `index.html` with a `title` that names the shortcut AND the gesture ("drag to draw; Shift for a square"); add its row to `TOOL_HINTS` in `ui/tool-hint.ts` (a compile error until you do); optionally a `kind:'tool'` command in `commands.ts` for a shortcut/palette entry.
- **Add a menu command / action:** add one entry to `COMMANDS` in `commands.ts` (id, label, accel, run, enabled). That single entry feeds the menu, keyboard, command palette, and context menu — do NOT wire those separately. Menu *structure* (which menu, in what order) is the `MENU_BAR` table in the same file, rendered by `ui/menus.ts`; the context menu's grouping is `ui/context-menu.ts`.
- **Add a panel (or panel section):** create `ui/<name>-panel.ts` exporting `setupX(state)` + `updateX(state)`; add its markup block in `index.html`; call `setupX` in the boot block and `updateX` in `onStateChange` (`main.ts`); if it's selection-dependent, add a visibility rule in `ui/inspector.ts`.
- **Fix a per-shape-type bug:** per-type geometry lives in `core/shape-adapters.ts` (`translateShapeGeometry`, `resizeBox`, `scalePoints`, `shapeToPathData`, `GEOM_ATTRS`) and the capability table in `core/shape-props.ts`. Prefer extending those over adding a new `switch (tag)`; cover **every** type incl. `path`/`polyline`/`polygon`/`line`/`group` and special-case frames. See recurring-bug #3.
- **Add a `data-*`-backed feature:** put the state in a `data-*` attribute on the drawing-layer element so it survives the history/save snapshot; regenerate any defs cache after rebuild. Register the attribute in [`docs/data-attributes.md`](docs/data-attributes.md).

## Asynchronous file saves

All file saves use `beginDocumentSave` before the first await. It snapshots content and captures the initiating tab through `core/document-save.ts`; `DocumentManager` owns completion. Never call `adoptSource` or `markClean` from a save completion against whichever tab is active. Preserve per-tab serialization, closed-tab handling, and unsaved edits during upload.
